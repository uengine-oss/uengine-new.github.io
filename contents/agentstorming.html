Agent Storming

사람과 AI가 함께 일하는 방식을 설계하는 워크숍입니다. 현장 참여자들이 실제 업무 흐름을 발견하고, 사람과 AI 에이전트가 협업하는 프로세스를 설계·실행·개선합니다.

설명서 다운로드 (PPTX) PDF로 보기 조직 규모별 시작점

Background

에이전트의 성패는 모델이 아니라 업무의 경계에서 갈립니다

기업이 AI 에이전트를 실무에 배치할 때 부딪히는 장애는 모델의 추론 능력보다 업무에 대한 이해가 부족한 데서 옵니다. 도메인 맥락이 없는 모델은 겉보기에 타당한 답을 내면서도 실제 업무 규칙을 어기고, 에이전트가 여럿이면 책임이 불분명해지고 컨텍스트 사이로 데이터가 새며 에이전트끼리 얽힙니다. 소프트웨어 공학에서 경계해 온 ‘진흙탕 덩어리(Big Ball of Mud)’가 에이전트 계층에서 되풀이되는 것입니다.

그래서 학계와 산업계의 아키텍트들은 도메인 주도 설계(DDD)와 이벤트 스토밍을 에이전트를 찾고 설계하는 도구로 쓰기 시작했습니다. AWS는 항공 운항과 고객 여정을 바운디드 컨텍스트 단위로 나눠 전담 에이전트를 도출했고, Orium 같은 컨설팅 기업은 이벤트 스토밍으로 수작업 병목을 진단해 도입 우선순위와 로드맵을 세웁니다.

이벤트 스토밍의 가치는 회사의 현실을 있는 그대로 드러낸다는 데 있습니다. 규정 문서에 없는 수작업 우회 절차와 시스템 단절, 비공식 협업이 벽에 드러나고, 그곳에 표시한 핫스팟이 에이전트 도입 기회가 됩니다. 도메인 이벤트는 트리거로, 커맨드는 도구 호출로, 정책은 가드레일로, 읽기 모델은 RAG 컨텍스트로 이어집니다.

Agent Storming은 이 흐름을 현장에서 실행할 수 있도록 절차와 판별 기준, 역할 분담, 도입 로드맵으로 정리한 유엔진의 워크숍 방식입니다.

uEngine Blog 이벤트 스토밍 기반 AI 에이전트 도출 스티커가 에이전트의 트리거·도구 호출·가드레일·책임 경계로 이어지는 방식과 도입 로드맵, 현실적인 한계를 다룬 글입니다. 글 전체 읽기 ↗

Why Agent Storming

에이전트 도입은 두 지점에서 동시에 실패합니다

엔터프라이즈 AI의 성패는 모델의 크기에 있지 않습니다. 업무의 경계와 책임을 에이전트에게 얼마나 명확히 전달하는가에 달려 있습니다.

어디에 쓸 것인가

기술을 중심으로 대상을 고르면 비용이 늘고, 사업 가치가 불분명해지며, 위험을 충분히 통제하지 못합니다. 에이전틱으로 소개된 사용 사례 상당수는 에이전트를 구현할 필요가 없습니다(Gartner).

구성 단위 설계의 실패

어떻게 나눌 것인가

기술이나 조직 형태를 기준으로 나누면 업무의 의미를 놓칩니다. 하나로 합치면 맥락 과부하가 생기고, 잘게 나누면 맥락 단절과 결정 충돌이 생깁니다. 에이전트 수를 늘리거나 줄이는 것만으로는 해결되지 않습니다.

Gartner의 권고 — 기존 업무에 에이전트를 덧붙이기보다, 업무 흐름을 처음부터 다시 설계하는 것이 성공으로 가는 길입니다.

Three Design Outputs

이벤트 스토밍 한 번으로 도입 위치와 경계, 설계 재료를 찾습니다

기술 중심 접근의 한계를 넘는 세 가지 설계 결과물입니다.

위치 · 어디에 쓸 것인가?

에이전트를 둘 곳

관찰, 판단, 행동이 가능한 핫스팟(Hotspot)을 에이전트 도입 기회로 바꿉니다.

해결하는 실패: 가치가 불분명한 도입 대상, 유행을 따른 사용 사례

책임 · 어디까지 맡길 것인가?

에이전트의 경계

용어와 규칙이 일관된 바운디드 컨텍스트(Bounded Context)를 책임 영역으로 지정합니다.

해결하는 실패: 맥락 과부하, 결정 충돌, 책임 혼선

재료 · 무엇으로 움직일 것인가?

에이전트의 설계 재료

워크숍에서 나온 9가지 아티팩트를 시스템 아키텍처와 코드로 옮깁니다.

해결하는 실패: 업무 규칙 위반, 규정 충돌에 따른 환각 현상

Workshop

5단계 워크숍으로 업무를 펼치고 경계를 긋습니다

업무에서 일어난 사건을 시간 순서로 펼치고, 경계를 그어 에이전트 후보를 구체적으로 정의합니다. 하나의 업무 여정을 함께 아는 8~12명이 참여하는 것을 권장합니다.

1

이벤트 펼치기

업무에서 일어난 사건을 과거형으로 적어 시간 순서로 배열합니다.

2

피벗 이벤트 표시

되돌릴 수 없는 전환점을 굵게 표시하여 기준을 세웁니다.

3

경계 긋기

피벗 이벤트와 용어, 담당의 변화를 기준으로 컨텍스트를 나눕니다.

4

핫스팟 표시

병목과 불명확한 지점을 찾아 빨간 마름모로 표시합니다.

5

기회와 명세

컨텍스트별 후보를 정하고 가장 성공률이 높은 첫 파일럿을 고릅니다.

From Stickies to Agents

벽에 붙인 스티커가 에이전트의 설계 재료가 됩니다

이벤트 스토밍 워크숍에서 나온 아티팩트 9가지를 AI 에이전트의 구성 요소로 옮기는 방법입니다.

스티커도메인에서의 의미AI 에이전트에서의 역할

바운디드 컨텍스트Bounded Context용어와 모델이 유효한 경계단일 에이전트의 책임 영역 또는 멀티 에이전트 팀의 우선순위와 경계

Validate the Opportunity

핫스팟이라고 모두 에이전트로 만들지 않습니다

핫스팟마다 에이전트가 스스로 관찰, 판단, 행동할 수 있는지 O.D.A로 검증합니다. 세 질문 중 하나라도 답이 ‘아니요’라면 규칙 자동화나 사람이 직접 수행하는 방안을 검토합니다.

Boundary

에이전트의 수가 아니라 경계의 위치를 정합니다

다섯 조건이 하나의 경계 안에서 일치할 때 구성 단위를 잘 나눌 수 있습니다. 바운디드 컨텍스트는 이를 하나로 묶는 설계 가설이며, 도메인과 에이전트가 일대일로 고정되는 것은 아닙니다. 권한, 상태, 비용, 위험, 책임을 기준으로 계속 검증하며 조정합니다.

조건정의DDD 요소막는 문제이벤트 스토밍에서 발견하는 지점
1. 일관된 용어프롬프트, 도구 설명, 데이터에서 쓰는 용어의 뜻이 같습니다유비쿼터스 언어맥락 과부하, 용어 혼선용어 변화 지점
2. 소유한 상태에이전트가 수정할 수 있는 데이터 범위가 정해져 있습니다애그리게잇결정 충돌애그리게잇
3. 명시된 규칙지켜야 할 업무 규칙이 경계 안에 모여 있습니다정책, 불변식업무 규칙 위반정책
4. 좁은 인터페이스다른 단위와는 정해진 사건을 통해서만 정보를 주고받습니다도메인 이벤트맥락 단절, 얽힌 의존 관계도메인 이벤트
5. 분명한 책임담당 팀과 사람의 승인 지점이 정해져 있습니다컨텍스트 소유 팀책임 혼선행위자

여러 신호가 겹치는 곳이 가장 확실한 경계 후보이며, 최종 경계는 반드시 도메인 전문가가 확정합니다. 보안이나 규제 등급이 다른 데이터 영역은 다른 신호와 관계없이 별도 컨텍스트로 분리합니다(Microsoft 기준).

단일 에이전트에서 시작합니다 — Microsoft와 OpenAI의 벤더 가이드는 모두 단일 에이전트로 시작하고, 분명한 경계가 있을 때만 나눌 것을 권고합니다.

가치 판단과 예외 처리를 맡습니다. 최고 권한과 최종 승인 권한을 갖습니다.

에이전트

패턴 분석, 초안 작성, 반복 수행을 맡습니다. 제한된 자율성을 갖고 사람의 승인 조건에 따라 작동합니다.

외부 시스템

기록 보존과 도구 실행을 맡습니다. 사람의 최종 승인 후 자동으로 작동합니다.

요청자, 에이전트, 담당자, 승인권자, 시스템을 다섯 개의 레인으로 나눠 누가, 언제, 무엇을 하는지 규정합니다. AI는 빠르고 효율적인 실행을 돕지만, 예외 상황의 처리와 최종 결정은 설계된 규칙에 따라 사람이 맡습니다.

Process GPT로 작게 검증합니다 — 대규모로 한꺼번에 도입하는 대신, 설계한 BPMN 모델을 Process GPT에서 가장 작은 단위로 시뮬레이션해 실제 지원 여부를 검증합니다. 자료에 담긴 Process GPT의 기능과 실행 화면은 실제 검증 전 제안 단계의 가설이며, 확정된 현행 기능 명세가 아닙니다.

Roadmap

전사 AI 에이전트 도입 5단계 로드맵

전체를 한 번에 전환하지 않습니다. 단일 파일럿을 제한된 그룹에 우선 배포한 뒤, 4주마다 평가하고 조정하며 인접 컨텍스트로 신중하게 넓혀 갑니다.

단계핵심 활동주요 산출물
1. 정렬 (Align)빅 픽처 이벤트 스토밍, 업무 이벤트 도출, 컨텍스트 경계 식별통합 타임라인 보드, 컨텍스트 후보안, 유비쿼터스 언어 용어집
2. 우선순위화 (Prioritize)핫스팟을 에이전트 기회로 전환, 영향과 위험 평가, 파일럿 선정에이전트 기회 백로그, 단일 파일럿 정의서, 핵심 성과 지표(KPI)
3. 아키텍처화 (Design)이벤트 스키마와 상태 모델 정의, 승인 가드레일 정의Architecture on a Page, OpenAPI 명세, 가드레일 명세
4. 구현 (Build)RAG 검색 기반 생성, 오케스트레이션 구축, 도구 호출 연동, 제한된 사용자에게 배포워크플로우 코드, 모니터링 대시보드, 성능 검증용 평가 모음
5. 반복과 확장 (Iterate & Scale)4주 단위 운영 데이터 평가, 프롬프트와 가드레일 조정, 인접 컨텍스트 확장에이전트 성능 평가 리포트, 컨텍스트 매핑 다이어그램, 거버넌스 지침

빅뱅 시도전체 자동화를 시도할 때의 예측 불가능성, 비용과 디버깅 난도 급증단일 핫스팟의 경량 파일럿으로 시작하고, 4주 단위로 평가한 뒤 확장합니다.

고위험 구간사람의 통제가 없을 때의 규제 위반과 법적 책임사람 승인(Human-in-the-loop) 가드레일을 컨텍스트 명세에 하드코딩합니다.
