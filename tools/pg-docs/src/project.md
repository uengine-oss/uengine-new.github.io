# 종합 과제 — 한빛오피스 A/S 접수 처리

> 한빛오피스의 A/S 처리 규정을 읽고, 에이전트의 보증 판정과 사람의 승인을 연결한 프로세스를 만듭니다. 무상·유상 두 건을 끝까지 실행한 뒤 KPI와 실행 분석으로 처리 과정을 돌아봅니다.

## 이번에는 스스로 완성합니다

여러분은 한빛오피스의 장진영 영업팀장입니다. 사무 가구를 구매한 고객사의 A/S 요청을 접수부터 완료 보고까지 처리하려고 합니다. 장진영은 서비스 책임도 겸임합니다. 접수와 견적, 수리 결과 기록은 김민지가 맡고, 재무 담당 박서연은 일정 금액 이상의 비용을 확인합니다.

이번 장은 정해진 화면을 그대로 따라 하는 실습이 아니라 **규정을 읽고 정의를 만들며, 실행으로 확인하는 과제**입니다. 생성된 이름이나 화면 구성이 예시 문장과 같을 필요는 없습니다. 규정의 조건, 담당자, 처리 순서가 맞아야 합니다.

필수 과제를 먼저 마친 뒤 결정표, 스킬, MCP 도구를 선택 과제로 붙입니다. 선택 과제를 하지 않아도 두 건의 실행과 KPI 측정, 분석까지는 완료합니다.

## 준비물과 완성할 흐름

실습 문서는 [한빛오피스 A/S 처리 규정(PDF)](files/hanbit-as-policy.pdf)입니다. 내려받아 제1조부터 제7조까지 읽습니다. 김민지와 박서연의 계정을 사용할 수 있는지도 확인합니다.

정의에는 **무상·유상을 나누는 갈림길**과 **유상 수리비 50만 원을 기준으로 재무 확인 여부를 나누는 갈림길**이 필요합니다. 승인·반려에 따른 진행과 되돌아가는 경로도 빠뜨리지 않습니다.

| 구간 | 규정에 맞는 흐름 |
|---|---|
| 접수와 보증 판정 | 김민지 접수 → 에이전트 보증 판정 |
| 무상 | 방문 수리 → 완료 보고 |
| 유상, 50만 원 미만 | 유상 견적 → 장진영 승인 → 방문 수리 → 완료 보고 |
| 유상, 50만 원 이상 | 유상 견적 → 장진영 승인 → 박서연 확인 → 방문 수리 → 완료 보고 |
| 반려 | 사유 기록 → 유상 견적으로 복귀 → 수정 금액에 따른 승인 절차 |

!!! note "갈림길 두 개를 확인하는 뜻"
    무상·유상과 금액 기준이라는 두 가지 업무 조건을 확인한다는 뜻입니다. 승인·반려를 표현하는 방식에 따라 흐름도의 마름모 수는 더 많을 수 있습니다. 개수만 맞추려고 반려 경로를 없애지 않습니다.

## 과제 2 — 딥 에이전트로 프로세스를 만듭니다

참고: [12장 — 문서로 프로세스 만들기](document-process.html)

<ol class="steps" markdown="1">
<li markdown="1">규정을 고른 대화에서 「딥 에이전트」에게 프로세스 생성을 요청합니다. 아래 문장을 출발점으로 사용합니다.</li>
<li markdown="1">초안에서 보증 판정은 에이전트가 맡고, 승인과 비용 확인은 사람이 맡는지 살펴봅니다.</li>
<li markdown="1">초안을 확인하고 생성을 진행합니다. 에이전트를 고르는 확인 창에서는 보증 판정 단계에 필요한 에이전트를 선택합니다.</li>
</ol>

> 선택한 한빛오피스 A/S 처리 규정대로 「A/S 접수 처리」 프로세스를 만들어 줘. 김민지가 접수하고 유상 견적을 작성해. 보증 판정은 규정을 참고하는 에이전트가 맡고 결과와 근거를 남겨 줘. 무상 건은 방문 수리로, 유상 건은 견적과 승인으로 이어 줘. 장진영이 유상 수리비를 승인하고, 50만 원 이상이면 그 뒤 박서연이 비용을 확인해. 반려하면 사유를 적고 유상 견적으로 돌아가게 해 줘. 방문 수리 결과는 김민지가 기록하고, 완료 보고에는 처리일·조치 내용·청구 금액을 넣어 줘. 접수 후 5영업일 안에 방문한다는 규정도 반영해 줘.

접수 폼에는 고객사, 제품명, 구매일, 증상, 방문 희망일이 필요합니다. 보증 판정과 견적에 쓸 접수일, 사용자 과실 여부, 방문 지역도 확인할 수 있어야 합니다. 정보가 없는데 에이전트가 임의로 판단하도록 두지 않습니다.

## 과제 3 — 원문과 대조하여 고칩니다

참고: [12장 — 문서로 프로세스 만들기](document-process.html)

생성 완료 안내만으로 과제가 끝나지 않습니다. 규정과 정의를 나란히 보며 아래 항목을 확인합니다.

<ol class="steps" markdown="1">
<li markdown="1">무상 조건이 「구매 후 2년 이내이면서 사용자 과실이 아님」인지 확인합니다.</li>
<li markdown="1">출장비가 서울·경기 3만 원, 그 밖의 지역 5만 원인지 확인합니다.</li>
<li markdown="1">50만 원에 정확히 해당하는 건도 장진영 승인 뒤 박서연 확인으로 가는지 확인합니다.</li>
<li markdown="1">반려 사유를 적는 곳과 유상 견적으로 돌아오는 경로를 확인합니다.</li>
<li markdown="1">완료 보고 항목과 접수 후 5영업일 이내 방문 조건을 확인하고, 다른 부분을 구체적으로 고쳐 달라고 요청합니다.</li>
</ol>

예를 들어 재무 확인이 팀장 승인보다 앞에 있다면 다음처럼 요청합니다.

> 규정 제5조와 다릅니다. 유상 수리비가 50만 원 이상이면 장진영이 먼저 승인하고 박서연이 그 뒤 비용을 확인하도록 고쳐 주세요. 반려하면 사유를 남기고 유상 견적으로 돌아가야 합니다.

수정한 뒤 같은 항목을 다시 확인합니다. 방문 기한을 문장으로 적었다고 자동으로 일정이 지켜지는 것은 아닙니다. 실행에서도 접수일과 방문일을 비교합니다.

## 과제 4 — 레인 담당자를 지정합니다

참고: [5장 — 조직도와 역할 담당자](organization.html)

<ol class="steps" markdown="1">
<li markdown="1">정의를 편집하고, 사람이 맡는 레인마다 「직접 사용자 선택」으로 아래 담당자를 지정합니다.</li>
<li markdown="1">보증 판정 단계는 선택한 에이전트가 맡는지 확인합니다.</li>
<li markdown="1">담당자를 지정한 정의를 버전으로 저장합니다.</li>
</ol>

| 역할 | 담당자 |
|---|---|
| 접수·유상 견적·방문 수리 결과 기록·완료 보고 | 김민지 |
| 영업팀장·서비스 책임 | 장진영 |
| 재무 담당·비용 확인 | 박서연 |
| 보증 판정 | 규정을 참고하는 에이전트 |

방문 수리 단계에서는 실습용 수리 결과를 기록합니다. 새로운 수리 담당자 계정을 추가할 필요는 없습니다.

## 과제 5 — 두 건을 끝까지 실행합니다

참고: [6장 — 실행하고 할 일 처리하기](process-run.html) · [7장 — 승인과 반려](gateway.html) · [13장 — 에이전트가 맡는 단계 실행하기](agent-steps.html)

아래 두 건을 각각 실행합니다. 고객사 이름과 접수일은 실습용으로 정하고, 구매일은 접수일을 기준으로 각각 1년 전과 3년 전의 날짜를 적습니다. 방문 희망일은 접수 후 5영업일 안에서 정합니다.

| 입력 항목 | 가 — 의자 바퀴 파손 | 나 — 모션 데스크 모터 교체 |
|---|---|---|
| 구매 시점 | 접수일로부터 1년 전 | 접수일로부터 3년 전 |
| 증상 | 정상 사용 중 의자 바퀴 파손 | 모션 데스크 모터 고장 |
| 사용자 과실 | 없음 | 없음 |
| 방문 지역 | 서울 | 부산 |
| 부품비 | 무상 건으로 청구하지 않음 | 600,000원 |
| 규정상 예상 경로 | 무상 → 방문 수리 | 유상 → 팀장 승인 → 재무 확인 → 방문 수리 |
| 규정상 청구 금액 | 0원 | 650,000원 |

의자 바퀴 파손이라는 증상만으로 무상을 확정할 수는 없습니다. 이번 입력은 **사용자 과실이 없는 경우**로 정합니다. 모션 데스크는 과실이 없어도 보증 기간을 지났으므로 유상이며, 부산 출장비 50,000원을 더합니다.

<ol class="steps" markdown="1">
<li markdown="1">장진영으로 「실행」을 열고 「역할 지정」의 담당자를 확인합니다.</li>
<li markdown="1">김민지의 접수 업무를 처리합니다. 담당자별 「나의 업무」에서 다음 할 일을 이어 갑니다.</li>
<li markdown="1">에이전트의 보증 판정 결과와 근거를 읽습니다. 구매일, 접수일, 과실 여부가 입력과 맞는지 확인합니다.</li>
<li markdown="1">유상 건은 김민지가 견적을 작성하고, 장진영의 승인 뒤 박서연의 비용 확인을 처리합니다. 각 단계의 값을 확인한 뒤 「제출 완료」를 누릅니다.</li>
<li markdown="1">두 건 모두 방문 수리 결과와 완료 보고를 입력합니다. 처리일, 조치 내용, 청구 금액을 빠뜨리지 않습니다.</li>
<li markdown="1">각 인스턴스가 「COMPLETED」인지 확인하고 「칸반보드」에서 완료된 업무를 살펴봅니다.</li>
</ol>

유상 건의 제출 점검에서 말하는 「승인 두 번」은 **장진영의 승인과 박서연의 비용 확인**을 뜻합니다. 두 사람의 처리 기록과 순서를 확인합니다. 카드 수만으로 승인 횟수를 판단하지 않습니다.

!!! note "예상과 실제를 구분합니다"
    표의 금액과 경로는 규정으로 계산한 예상입니다. 실제 실행에서 그 경로로 진행했는지는 여러분이 확인해야 합니다. 예상과 다르면 입력값, 에이전트 결과, 분기 조건을 살펴보고 고칩니다. 완료되지 않은 건을 완료했다고 제출하지 않습니다.

## 과제 6 — 보증 판정을 결정표로 만듭니다〔선택〕

참고: [15장 — 비즈니스 규칙(DMN)](dmn.html)

<ol class="steps" markdown="1">
<li markdown="1">보증 기간 충족 여부와 사용자 과실 여부를 입력으로, 무상·유상을 결과로 하는 결정표를 만듭니다.</li>
<li markdown="1">2년 이내·과실 없음, 2년 이내·과실 있음, 2년 초과의 경우를 시험합니다. 정확히 2년인 경우도 확인합니다.</li>
<li markdown="1">규칙을 에이전트에 붙이고, 같은 조건을 물었을 때 결정표와 일치하는지 확인합니다.</li>
</ol>

선택 과제 결과에는 결정표와 시험에 쓴 입력, 실제 답을 함께 남깁니다. 기간을 충족하는지만 보고 무상으로 정하지 않도록 주의합니다.

## 과제 7 — KPI를 측정하고 병목을 찾습니다

참고: [17장 — 전략 보드](strategy.html) · [16장 — 실행 분석](analytics.html)

<ol class="steps" markdown="1">
<li markdown="1">전략 보드에서 A/S 처리 개선에 해당하는 전략목표를 정합니다.</li>
<li markdown="1">「KPI 추가」로 「A/S 평균 처리시간」을 추가합니다. 접수부터 완료 보고까지의 시간을 대상으로 하고, 측정 단위를 명확히 적습니다.</li>
<li markdown="1">17장에서 익힌 방법으로 측정에 필요한 값을 준비하고 「측정 갱신」을 합니다. 실제 표시된 값과 측정 시점, 대상 건수를 기록합니다.</li>
<li markdown="1">분석 대시보드와 프로세스 분석 히트맵에서 이번 프로세스를 살펴봅니다. 시간이 오래 걸린 단계가 있는지 확인합니다.</li>
<li markdown="1">관찰한 단계와 개선 의견을 적습니다. 두 건만으로 판단하기 어렵다면 추가로 어떤 실행 기록이 필요한지 적습니다.</li>
</ol>

평균 처리시간과 「접수 후 5영업일 안에 방문」은 서로 다른 기준입니다. 전자는 완료 보고까지의 시간이고, 후자는 방문 기한입니다. 평균만 보고 모든 건이 방문 기한을 지켰다고 판단하지 않습니다.

실습을 빠르게 진행했다면 실제 업무의 대기시간을 대표하지 않을 수 있습니다. 분석 화면에서 확인한 사실과 앞으로 확인할 가설을 구분합니다.

## 과제 8 — 완료 보고를 재사용합니다〔선택〕

참고: [11장 — 스킬](skills.html) · [14장 — MCP 도구](mcp-hub.html)

<ol class="steps" markdown="1">
<li markdown="1">처리일·조치 내용·청구 금액이 빠지지 않는 완료 보고 형식을 스킬로 만들고, 업로드하여 에이전트에 붙입니다.</li>
<li markdown="1">14장에서 익힌 「설정 › MCP 서버」의 office 등록과 에이전트 도구 연결을 확인합니다.</li>
<li markdown="1">완료된 건의 기록을 바탕으로 MCP 도구를 사용해 완료 보고서를 문서로 만듭니다. 생성된 문서를 열어 원래 기록과 대조합니다.</li>
</ol>

보고서에 없는 조치 내용을 에이전트가 덧붙이지 않았는지 확인합니다. 스킬 적용 결과와 문서 생성 결과는 각각 확인한 범위만 제출합니다.

## 제출물과 충족 여부

아래 표를 점검표로 사용합니다. 점수 대신 각 항목의 충족 여부와 근거 위치를 적습니다. 선택 과제를 하지 않았다면 「미수행」으로 표시합니다.

| 구분 | 제출물·평가 기준 | 충족 여부 |
|---|---|---|
| 필수 | 규정과 대조한 정의 흐름도: 무상·유상 및 50만 원 기준 갈림길, 반려 후 견적 복귀 | □ 충족 □ 보완 |
| 필수 | 레인 담당자: 김민지·장진영·박서연과 보증 판정 에이전트 | □ 충족 □ 보완 |
| 필수 | 두 인스턴스가 모두 COMPLETED이며 유상 건의 승인 두 단계 기록이 있음 | □ 충족 □ 보완 |
| 필수 | 두 건의 에이전트 보증 판정 결과와 근거를 사람이 확인함 | □ 충족 □ 보완 |
| 필수 | 완료 보고에 처리일·조치 내용·청구 금액이 있으며 방문 기한을 확인함 | □ 충족 □ 보완 |
| 필수 | A/S 평균 처리시간의 실제 측정값·단위·측정 시점·대상 건수 | □ 충족 □ 보완 |
| 필수 | 분석 화면과 병목 관찰 또는 추가 확인이 필요한 이유 | □ 충족 □ 보완 |
| 선택 | 보증 판정 결정표와 경계 조건을 포함한 시험 결과 | □ 충족 □ 보완 □ 미수행 |
| 선택 | 완료 보고 스킬과 적용 결과 | □ 충족 □ 보완 □ 미수행 |
| 선택 | MCP 도구로 만든 완료 보고 문서와 원래 기록의 대조 | □ 충족 □ 보완 □ 미수행 |

## 자주 막히는 곳

| 상황 | 확인할 내용 |
|---|---|
| 실행 담당자가 모두 장진영으로 보입니다. | 레인 담당자를 지정하지 않으면 실행하는 사람으로 채워집니다. 「직접 사용자 선택」과 실행 창의 담당자를 확인합니다. [5장](organization.html) |
| 저장할 때 「BPMN 검증 결과」 경고가 나옵니다. | 내용을 읽고 「무시하고 저장」으로 진행합니다. 저장한 뒤 필요한 조건과 경로가 있는지 확인합니다. [13장](agent-steps.html) |
| 다음 폼이 비어 있습니다. | 앞 단계 값은 저절로 옮겨 오지 않습니다. 「이전 작업 입력 내역」을 읽고 필요한 값을 입력합니다. [6장](process-run.html) |
| 반려 의견을 썼는데 승인으로 진행합니다. | 검토의 고르기 칸은 처음에 「승인」이 선택되어 있습니다. 제출 전에 「반려」로 바꿉니다. [7장](gateway.html) |
| 에이전트의 계산이나 날짜가 이상합니다. | 결과를 사람이 규정과 입력값에 대조합니다. 계산과 날짜를 그대로 믿고 제출하지 않습니다. [13장](agent-steps.html) |
| 딥 에이전트 생성이 보류되거나 초안이 다릅니다. | 생성은 회차마다 다를 수 있습니다. 필요한 조건을 구체적으로 적어 다시 요청합니다. [12장](document-process.html) |
| 확인 창에서 생성이 멈춘 듯합니다. | 여러 쪽이면 「다음」으로 넘어가 마지막에 「응답 제출」을 합니다. [7장](gateway.html) |
| 실행 창을 닫았는데 할 일이 남습니다. | 열고 닫기만 해도 첫 단계 할 일이 남을 수 있습니다. 새 실행 전에 「나의 업무」를 확인합니다. [5장](organization.html) |

## 마치며

이 튜토리얼에서는 반복 업무를 말로 설명하고, 정의를 살펴 고치고, 사람과 에이전트가 함께 실행하는 방법을 익혔습니다. 마지막 과제에서는 문서의 규칙이 흐름과 담당자, 실행 기록에 제대로 반영되는지 직접 확인합니다.

새 업무를 만들 때도 규정 읽기, 초안 대조, 담당자 지정, 실행 확인, 측정의 순서로 접근합니다. 기능과 순서를 다시 찾을 때는 부록 [한눈에 보기](cheatsheet.html)를, 막히는 부분을 확인할 때는 [자주 묻는 질문](faq.html)을 활용합니다.

!!! exercise "확인 문제"
    1. 의자 건을 무상으로 판정하려면 구매 기간 외에 무엇을 확인해야 하며, 판정 근거는 왜 남겨야 하나요?
    2. 부산의 모터 교체 건은 얼마를 기준으로 승인 경로를 정하며, 반려되면 어디로 돌아가나요?
    3. 두 인스턴스가 완료되고 평균 처리시간이 짧게 나왔다면, A/S 업무가 충분히 개선되었다고 말할 수 있나요?

<details class="answer" markdown="1"><summary>답</summary>

1. 사용자 과실이 없는지 확인해야 합니다. 판정 근거를 남기면 사람이 규정과 입력을 대조하고, 잘못된 판단의 원인을 찾을 수 있습니다.
2. 부품비 60만 원에 부산 출장비 5만 원을 더한 65만 원을 기준으로 정합니다. 장진영 승인 뒤 박서연이 확인하며, 반려하면 사유를 남기고 유상 견적으로 돌아갑니다.
3. 두 건만으로는 충분하지 않습니다. 측정 범위와 단위, 방문 기한 준수, 단계별 대기시간을 함께 확인하고 실제 업무 기록을 더 모아 판단해야 합니다.

</details>
