# 브라우저 에이전트와 보관함

> 로그인이 필요한 사이트의 일을 비서에게 맡깁니다. 비서가 브라우저를 직접 조작하는 모습을 실시간으로 보고, 계획을 확인하고, 필요하면 손을 넘겨받아 직접 입력합니다. 비밀번호·카드 번호·인증 코드는 보관함이 맡아 AI 모델에게는 한 번도 보이지 않는다는 것, 그리고 두 겹의 열쇠로 그것을 어떻게 지키는지까지 확인합니다.

## 왜 브라우저 에이전트인가

5장의 메일은 비서가 바로 읽을 수 있었습니다. 하지만 거래처 포털에서 세금계산서를 발행하고, 자재몰에서 주문 내역을 확인하고, 관리 콘솔에서 설정을 바꾸는 일은 프로그램끼리 연결할 통로가 없어 **로그인한 브라우저**로만 할 수 있습니다. 브라우저 에이전트는 서버에 있는 브라우저를 여러분 대신 조작합니다. 페이지를 읽고, 누르고, 입력하고, 결과를 정리해 줍니다.

걱정되는 것은 두 가지입니다. **비밀번호를 AI에게 줘도 되나?** 그리고 **AI가 마음대로 결제하면?** Process GPT Lite는 이렇게 답합니다.

| 걱정 | 장치 |
|---|---|
| 비밀번호·카드 번호가 AI에게 간다 | 보관함이 값을 맡고, 입력은 서버가 직접 합니다. 모델은 “여기에 비밀번호를 넣어”라고만 말할 수 있습니다 |
| 화면 사진에 비밀이 찍힌다 | 모델이 보는 페이지 내용에서는 비밀 칸의 값을 지우고, 화면 사진에서는 비밀 칸을 검게 가립니다. 실시간 화면에서도 카드 칸은 점으로 보입니다 |
| 결제·전송·삭제를 마음대로 한다 | 그런 동작 직전에는 반드시 **승인 카드**를 띄우고, 사람이 「승인」해야 진행합니다 |
| 일이 엉뚱하게 흘러간다 | 실시간 화면과 계획을 보고 있다가 언제든 「직접 제어」로 넘겨받거나 「작업 취소」 |

## 연습용 사이트 — 테스트 상점

이 장은 저장소에 들어 있는 **테스트 상점**으로 실습합니다. 이메일·비밀번호 로그인, 휴대폰 인증 코드, 카드 결제 화면이 있는 작은 연습용 사이트이고, 실제 돈은 오가지 않습니다. 설치할 때 받은 저장소 폴더에서 이렇게 엽니다(Node.js가 필요합니다).

```bash
node server/test/fixtures/shop.mjs 8811
# test shop on http://127.0.0.1:8811  (login demo@shop.test / otp 246810)
```

| 항목 | 값 |
|---|---|
| 주소 | `http://127.0.0.1:8811` |
| 로그인 | `demo@shop.test` / `Correct-Horse-42` |
| 휴대폰 인증 코드 | `246810` |
| 연습용 카드 | `4242 4242 4242 4242`, 만료 `12/30`, CVC `123` |

!!! note "설치 번들(Docker)에서는"
    설치 번들에서는 브라우저가 서버 컨테이너 안에서 돌므로, 내 PC에서 띄운 테스트 상점은 `127.0.0.1` 대신 `host.docker.internal:8811`처럼 컨테이너에서 보이는 주소로 부르세요. 사내망의 실제 사이트에 쓸 때도 서버가 그 주소에 닿을 수 있어야 합니다.

## 따라 하기 1 — 처음 가는 사이트에 로그인

입력창에 이렇게 보냅니다.

```text
테스트 상점(http://127.0.0.1:8811/login)에 로그인해서 내 최근 주문 내역을 알려줘.
```

비서가 “로그인해서 최근 주문 내역 확인해 드릴게요” 하고, 채팅에 **작업 카드**가 생깁니다. 카드에는 서버 브라우저의 화면이 실시간으로 비칩니다. 입력창 위 상태 줄에는 “127.0.0.1 여는 중”, “페이지 읽는 중”처럼 지금 하는 동작이 나옵니다.

에이전트가 비밀번호 칸을 만나면 멈추고 **로그인 카드**를 올립니다. 처음 가는 사이트라 보관함에 저장된 로그인이 없기 때문입니다. 작업 카드에는 주황색 「조치 필요」가, 입력창 왼쪽에는 주황색 경고 버튼이 생깁니다. 경고 버튼을 누르면 답해야 할 카드로 화면이 옮겨 갑니다.

![로그인 카드 — 여기 적은 값은 채팅에도 모델에도 가지 않고 보관함으로 갑니다](img/browser-login-request.webp)

<ol class="steps" markdown="1">
<li>로그인 카드에 <code>demo@shop.test</code>와 <code>Correct-Horse-42</code>를 넣고 「로그인」을 누릅니다.</li>
<li>카드가 “127.0.0.1 로그인 저장됨”으로 바뀌고, 서버가 저장한 값을 페이지에 직접 넣어 로그인합니다.</li>
<li>사이트가 휴대폰 인증 코드를 묻자, 이번에는 <b>인증 코드 카드</b>가 뜹니다. “입력한 값은 이 단계에만 쓰이고 저장되지 않아요.” 일회용 값은 보관함에 남기지 않습니다. <code>246810</code>을 넣고 「입력」을 누릅니다.</li>
</ol>

![인증 코드 카드 — 일회용 값은 페이지에 바로 넣고 버립니다](img/browser-otp-card2.webp)

1분 남짓 지나 작업이 끝나면 카드 아래쪽 알약(작업 제목)을 눌러 **계획**을 볼 수 있습니다. 에이전트가 처음에 세운 단계와, 끝낸 단계의 초록 점, 단계마다 남긴 메모가 보입니다. 그 아래에는 결과 요약이 오고, 요약 끝에는 **실제로 한 일** 목록(“보관함의 아이디 입력”, “'로그인' 누르기”, “127.0.0.1 열기”…)이 붙습니다. 이 목록은 에이전트의 말이 아니라 서버가 기록한 브라우저 동작이므로, 요약과 맞는지 견줘 볼 수 있습니다.

![작업 진행 상황 — 다섯 단계 모두 끝남. 아래로 “인증 코드 전달됨 · 저장하지 않음”과 주문 요약](img/browser-plan.webp)

**확인할 것**: 요약에 주문 **#A-1001 무선 이어폰 89,000원 (배송 중)** 이 있고, “휴대폰으로 받은 6자리 인증 코드 전달됨 · 저장하지 않음” 줄과 「실제로 한 일」 목록이 있으면 됩니다. 요약에 주문이 빠져 있으면 계획의 메모에서 찾아보세요. 같은 요청을 한 번 더 보내 보면, 이번에는 로그인 카드 없이 **보관함에서 자동으로** 로그인하고 인증 코드만 묻습니다.

## 따라 하기 2 — 크게 보고, 직접 제어하기

작업 카드의 확장 버튼(↗)이나 「조치 필요」를 누르면 화면 전체로 크게 봅니다.

![크게 보기 — 아래에 「계획 0/6」, 「직접 제어」, 「작업 취소」, 그 밑에 멈춘 이유. 오른쪽 아래에 답해야 할 인증 코드 카드](img/browser-handoff.webp)

| 버튼 | 하는 일 |
|---|---|
| 「계획 n/m」 | 단계 목록을 펼칩니다 |
| 「직접 제어」 | 내가 넘겨받습니다. 화면 테두리가 주황색이 되고, 화면을 누르거나 키보드로 입력하면 그대로 서버 브라우저에 전달됩니다 |
| 「제어 돌려주기」 | 다시 에이전트에게 넘깁니다. 에이전트는 페이지를 다시 읽고 이어서 합니다 |
| 「작업 취소」 | 작업을 멈춥니다. 채팅에 “작업을 취소했어요.”가 남습니다 |

직접 제어는 캡차처럼 사람이 풀어야 하는 화면이나, 에이전트가 같은 곳에서 헤맬 때 씁니다. 같은 요청을 한 번 더 보내고, 인증 코드 화면에서 「직접 제어」를 누른 뒤 화면 안의 코드 칸에 직접 `246810`을 입력해 봅니다.

![직접 제어 중 — 주황 테두리, 버튼이 「제어 돌려주기」로 바뀌었습니다. 코드 칸의 글자는 점으로 가려집니다](img/browser-takeover.webp)

Enter로 확인한 뒤 「제어 돌려주기」를 누르면, 쓰지 않은 인증 코드 카드는 “요청이 만료됐어요”로 바뀌고 에이전트가 로그인된 페이지에서 이어 갑니다.

!!! tip "직접 입력한 로그인도 보관함으로"
    직접 제어 중에 로그인 폼이나 카드 폼에 값을 넣고 제출하면, 보관함이 그 값을 알아채 “저장할지 확인해 주세요” 카드를 올립니다. 「저장」을 누르면 다음부터는 에이전트가 그 값을 씁니다. 저장하지 않으면 버립니다.

### 작업이 이미 돌고 있을 때 — 줄 서기

브라우저는 사용자마다 하나이므로 작업은 한 번에 하나씩 합니다. 앞 작업이 끝나기 전에 다른 브라우저 작업을 시키면 새 작업은 **줄을 섭니다.** 작업 카드에 「대기 · (작업 제목)」이 붙고, 채팅에 “브라우저는 한 번에 한 작업만 해요. 앞 작업 …이(가) 끝나거나 취소되면 … 이어서 시작할게요.”라는 안내가 옵니다. 앞 작업이 끝나면 저절로 시작합니다.

![로그인 카드를 기다리는 작업이 있는 동안 결제를 시킨 모습 — 새 작업 카드에 「대기 · 무선 이어폰 결제」와 “앞 작업 ‘최근 주문 내역 확인’이(가) 끝나면 시작해요”. 오른쪽 아래 ×로 이 작업만 취소합니다](img/browser-queued.webp)

| 하고 싶은 것 | 하는 법 |
|---|---|
| 앞 작업을 마저 하기 | 앞 작업의 카드(로그인·인증 코드)에 답합니다. 줄을 선 작업과 상관없이 그대로 닿습니다 |
| 줄 선 작업만 그만두기 | 대기 카드의 ×(작업 취소). “시작하기 전에 취소했어요.”로 바뀌고 앞 작업은 계속됩니다 |
| 앞 작업을 그만두기 | 앞 작업 카드의 ×나 「작업 취소」. 그다음 줄 선 작업이 시작됩니다 |

에이전트가 브라우저에서 아무것도 하지 않은 채 끝내려 하면 서버가 한 번 되돌려 보냅니다. 그래도 아무 동작도, 기록한 사실도, 페이지 변화도 없으면 「완료」 대신 **「확인 필요」**로 남기고 “브라우저에서 아무 동작도 하지 못한 채 작업이 끝났어요”라고 알립니다. 그때는 같은 요청을 다시 보내거나 직접 제어로 확인하세요.

## 따라 하기 3 — 카드로 결제하고 승인하기

```text
테스트 상점(http://127.0.0.1:8811/checkout)에서 무선 이어폰 1개를 내 카드로 결제해 줘.
```

보관함에 카드가 없으므로 이번에는 **결제 카드** 카드가 뜹니다. 소유자 이름, 카드 번호 `4242 4242 4242 4242`, `12/30`, `123`을 넣고 「카드 저장」을 누릅니다. 카드는 “카드 저장됨 · Visa •••• 4242”로 바뀌고, 서버가 결제 폼을 채웁니다.

결제 버튼을 누르기 직전, 에이전트는 반드시 멈추고 **승인 카드**를 올립니다. 무엇을, 얼마에, 어느 카드로 하는지가 적혀 있습니다.

![승인 카드 — 89,000원, Visa •••• 4242. 위 실시간 화면의 카드 칸은 모두 점으로 가려져 있습니다](img/browser-approve.webp)

「승인」을 누르면 결제를 마치고 주문 번호를 알려 줍니다. 「취소」를 누르면 결제하지 않습니다.

![결제 완료 — 카드 저장됨, 승인, 그리고 주문 #A-2002 결제 완료 요약](img/browser-paid.webp)

**확인할 것**: 승인 카드에 금액과 **Visa •••• 4242** 가 있고, 승인 뒤 요약에 새 주문 번호(이번 실행은 #A-2002)가 있으면 됩니다. 카드 번호 전체는 채팅 어디에도 보이지 않아야 합니다.

!!! tip "승인은 승인 카드로"
    결제·전송·삭제 직전의 승인은 지시에 쓰지 않아도 기본으로 걸립니다. “승인을 받아”라고 지시에 넣으면 에이전트가 결제 화면까지 가지 않고 “승인해 주시면 진행하겠습니다”라는 보고만 하려 할 때가 있습니다(그렇게 아무 동작 없이 끝나면 작업 카드가 「확인 필요」로 남습니다). 위처럼 할 일만 말하고 승인은 승인 카드로 하세요.

## 빠른 판단 — 큰 모델을 덜 부르는 법

브라우저 작업은 동작마다 큰 모델을 부릅니다(화면 사진까지 읽으므로 비쌉니다). 그래서 짧은 판단은 작은 **판단 모델**에게 먼저 묻습니다([4장](contexts.html)의 대화 맥락 판단과 같은 모델입니다).

| 묻는 것 | 확실하면 |
|---|---|
| 이 페이지는 아직 불러오는 중인가? | 큰 모델에게 묻지 않고 잠깐 기다립니다(상태 줄 “페이지 기다리는 중”) |
| 로그인 벽이나 캡차인가? | 사람이 없는 작업이면 무리하지 말라고 미리 알려 줍니다 |
| 지금까지 메모한 사실로 목표에 다 답할 수 있나? | 더 돌아다니지 않고 바로 정리해 끝냅니다 |

판단 모델이 확신할 때만 이렇게 하고, 아니면 평소대로 큰 모델이 판단합니다. 개발팀이 재 본 바로는 작업 한 번에 큰 모델을 부르는 횟수가 약 21% 줄었습니다. 이 기능은 대화 맥락 라우터가 연결된 서버에서만 켜지므로, 현재 설치 번들에서는 기본으로 꺼져 있습니다.

## 보관함 — 비밀은 어디에, 어떻게

브라우저 작업 중 저장한 로그인과 카드는 **보관함**에 있습니다. 직접 넣을 수도 있습니다.

| 어디 | 무엇 |
|---|---|
| 설정 › 계정 | 연결(Google 등), 사이트 로그인, API 키. 「+ 로그인 추가」, 「+ API 키 추가」 |
| 설정 › 지갑 | 결제 카드. 화면엔 카드사와 끝 네 자리, 저장일, 사용 횟수만 |
| 설정 › 보안 | 암호화 방식, 마스터 키 정보, 「검증」, 보관함 활동 기록 |

저장된 비밀번호는 다시 보여 주지 않습니다. 「설정 › 계정」에서 로그인을 누르면 **새 값으로 바꾸기**만 됩니다.

### 금고 안의 금고 — 마스터 키와 데이터 키

보관함은 **봉투 암호화**를 씁니다. 금고 비유로 보면 이렇습니다.

1. 비밀번호·카드 같은 **항목**은 사용자마다 따로 만든 열쇠, **데이터 키**(화면에는 DEK)로 잠급니다.
2. 그 데이터 키는 다시 **마스터 키**(화면에는 KEK)로 잠가서 데이터베이스에 둡니다.
3. 마스터 키는 데이터베이스 **밖**에 있습니다 — 서버의 키 파일이나, 설치 번들이면 설치 폴더의 설정 파일 `.env`([1장](install.html)).

그래서 데이터베이스 백업이 통째로 새어 나가도 마스터 키 없이는 아무것도 열 수 없습니다. 항목은 그 사용자·그 사이트에 묶여 잠기므로, 다른 사용자나 다른 사이트의 자리로 옮겨 놓아도 열리지 않습니다. 마스터 키를 바꾸거나 데이터 키를 새로 만드는 일은 운영자가 합니다([25장](admin.html)).

「설정 › 보안」의 「검증」을 누르면, 서버가 내 항목을 실제로 열어 보고 변조·이동에 어떻게 반응하는지 확인합니다. 값은 보여 주지 않습니다.

검증 결과 아래의 **보관함 활동**에는 누가 언제 무엇을 했는지가 남습니다. “로그인 저장 · 나”, “로그인 아이디 · 브라우저 작업에 입력 · 브라우저 에이전트”처럼, 값을 쓴 주체가 **모델이 아니라 브라우저 에이전트(서버)** 라는 것을 확인할 수 있습니다.

    1. 테스트 상점 로그인을 「설정 › 계정」에서 지운 뒤, 따라 하기 1의 요청을 다시 보내 보세요. 어떤 카드가 다시 뜨나요?

    4. 「설정 › 보안 › 보관함 활동」에서 카드가 결제 폼에 들어간 기록을 찾아보세요. 누가 넣었다고 나오나요?

<details class="answer" markdown="1"><summary>답</summary>

1. 저장된 로그인이 없으므로 로그인 카드가 다시 뜹니다. 지운 기록은 보관함 활동에 “로그인 삭제 · 나”로 남습니다.
2. 인증 코드는 한 번 쓰면 끝나는 값이라 저장해 둘 이유가 없고, 남겨 두면 위험만 늘기 때문입니다. 카드에 “입력한 값은 이 단계에만 쓰이고 저장되지 않아요”라고 쓰여 있습니다.
3. 백업에 있는 것은 데이터 키로 잠긴 항목과, 마스터 키로 잠긴 데이터 키뿐입니다. 마스터 키는 데이터베이스 밖(서버 키 파일이나 `.env`)에 있으므로, 백업만으로는 데이터 키를 풀 수 없고 따라서 항목도 풀 수 없습니다.
4. “카드 번호 · 브라우저 작업에 입력”처럼 남고, 주체는 “브라우저 에이전트”입니다. 모델은 값을 받은 적이 없습니다.
</details>
