# 인제스천 바이브 코딩: PDF → 조·항·호 → Neo4j

> Claude Code에 적재 코드를 맡겨 법령 PDF 9개를 조·항·호·목 노드와 인용·위임·벌칙 관계로 Neo4j에 넣습니다. 수치 확인에 그치지 않고 조 수와 표본 조문을 PDF 원문과 대조한 뒤, 오류를 구체적으로 짚어 수정을 요청합니다.

## 무엇을 · 왜

5장의 스키마 가운데 **구조층·참조층·용어층**을 채웁니다. 조문을 나누고 「제N조제M항」 인용을 찾는 작업은 규칙(들여쓰기·정규식)으로 처리하고, LLM은 코드를 작성하는 데만 사용합니다. 따라서 같은 PDF로 다시 실행하면 같은 그래프가 나옵니다. 조문 본문에서 주체와 의무를 뽑는 의미층(`Actor`·`Norm`)은 [7장](disambiguation.html)에서 다룹니다.

바이브 코딩에서 사람이 맡는 역할은 **검증**입니다. PDF를 파싱할 때는 띄어쓰기와 줄바꿈이 깨지기 쉬워, 이 장의 절반은 적재 결과를 원문과 대조하는 데 할애합니다.

## 만들어진 파일

| 파일 | 하는 일 |
|---|---|
| `pyproject.toml`, `uv.lock`, `.python-version` | Python 3.12, 의존성 `pymupdf`·`neo4j`·`python-dotenv`. 실행은 `uv run …` |
| `parse_law.py` | PDF → `data/<법령>.json`. 각 줄의 x 좌표(들여쓰기)로 조·항·호·목을 나누고, 쪽 머리말·꼬리말을 제거하며, 부칙을 제외합니다. `[시행일: …]` 판본을 분리하고 줄바꿈 위치의 띄어쓰기를 추정합니다(`Joiner`) |
| `extract.py` | JSON → 노드·관계 행. 「제N조제M항」 인용을 분석해 `REFERS_TO`·`IMPLEMENTS`·`PENALIZES`·`CITES_LAW`를 생성합니다. 형량 문구로 `Sanction`을, 정의·약칭 문형으로 `Term`·`DEFINED_IN`·`MENTIONS`를 생성합니다. |
| `lawtext.py` | 정규화. 키용 `norm_key`(가운뎃점 7종 → `·`, 공백 제거), 전문 색인용 `search_text`(가운뎃점 → 공백) |
| `ingest.py` | `schema.cypher`의 제약·색인을 먼저 적용하고 `UNWIND $rows … MERGE`로 일괄 적재합니다. `--dry-run`·`--reset`·`--prune` |

`data/`는 PDF에서 다시 만들 수 있어 `.gitignore`에 포함했습니다. 핵심 코드를 발췌하면 다음과 같습니다(Claude가 작성한 코드이며 실행할 때마다 달라질 수 있습니다).

```python
# ingest.py — 행 묶음을 한 번에 MERGE
def merge_nodes(session, label, key, rows, extra_label=""):
    query = f"UNWIND $rows AS r MERGE (n:{label} {{{key}: r.{key}}}) SET n += r"
    if extra_label:
        query = f"UNWIND $rows AS r MERGE (n:{label} {{{key}: r.{key}}}) SET n:{extra_label}, n += r"
    for chunk in batches(rows):
        session.run(query, rows=chunk).consume()

def merge_edges(session, kind, rows):
    src_label, src_key, dst_label, dst_key = EDGE_ENDS[kind]
    query = (f"UNWIND $rows AS r "
             f"MATCH (a:{src_label} {{{src_key}: r.src}}) MATCH (b:{dst_label} {{{dst_key}: r.dst}}) "
             f"MERGE (a)-[e:{kind}]->(b) SET e += r.props")
    for chunk in batches(rows):
        session.run(query, rows=chunk).consume()
```

### 3. 오류를 구체적으로 짚어 수정 요청하기(P5)

「띄어쓰기 고쳐 줘」 대신 **어디가 · 어떻게 틀렸고 · 맞는 글은 무엇이며 · 고친 뒤 무엇으로 확인할지**를 적었습니다.

```text
시행령 제21조 머리글이 「동일한시ㆍ도에」로 붙었어. PDF 원문은 「동일한 시ㆍ도에」야. 줄바꿈 자리 띄어쓰기 규칙을 고쳐 줘.
고친 뒤 위험물안전관리법 3종에서 줄바꿈 자리 판정이 바뀐 곳의 개수와 예를 보여 주고, 법 제15조·시행령 제21조·시행규칙 제53조 본문을 PDF 와 다시 대조해. 다시 적재해서 노드·관계 수가 그대로인지 확인하고 커밋해 줘.
```

5분 39초 뒤 받은 보고의 주요 내용입니다.

- 규칙으로 판단하지 못해 붙여 둔 위치는 여전히 약 9%입니다(예: 「재해발생시|비상조치의」처럼 앞 낱말이 문서에 한 번만 나오는 경우).

### 4. 다시 실행해도 중복이 없는지 확인하기 — 그리고 남는 기존 데이터

P5에서 「노드·관계 수가 그대로인지」 물었는데 답은 「그대로가 아니다」였습니다. 노드 6,268 → 6,272, 관계 17,513 → 17,537. 띄어쓰기가 고쳐지면서 「(이하“위험물운반자”라 한다)」처럼 붙어 있던 약칭 4개가 새로 `Term`으로 생성되었고, `DEFINED_IN`이 10개, `MENTIONS`가 21개 늘고 7개 줄었습니다.

그런데 줄어야 할 `MENTIONS` 7개가 DB에 그대로 남아 있었습니다. **`MERGE`는 이미 있으면 유지하고 없으면 추가하기만 하므로**, 다시 실행해도 중복은 생기지 않지만 이번 추출에서 빠진 기존 노드·관계를 삭제하지는 않습니다. Claude는 `ingest.py`에 `--prune`(이 스크립트의 노드·관계 중 이번 추출에 없는 항목 삭제)을 더해 한 번 실행했고, 정확히 그 7개만 지워졌습니다. 삭제 명령이므로 승인 전에 코드를 읽고 1을 선택했습니다. 이후 옵션 없이 다시 실행해도 6,272 / 17,537로 유지되었습니다.

| 명령 | 쓰는 때 |
|---|---|
| `uv run ingest.py` | 일반적인 적재에 사용합니다. 다시 실행해도 중복이 생기지 않습니다. |
| `uv run ingest.py --prune` | 추출 규칙을 수정한 뒤 기존 데이터를 정리합니다. `data/`에 9개 법령이 모두 있을 때만(없는 법령의 노드도 지움) |
| `uv run ingest.py --reset` | 이 스크립트의 레이블이 붙은 노드를 모두 지우고 처음부터 적재합니다. |
| `uv run ingest.py --dry-run` | DB에 쓰지 않고 추출한 개수만 확인합니다. |

### 5. 시행 예정 조문

국가법령정보센터 PDF에는 시행일이 다른 판본이 같은 문서에 함께 실립니다. 폐기물관리법 제13조의2·제68조, 폐기물관리법 시행규칙 제10조는 현행 조문 뒤에 `[시행일: …]`이 붙은 같은 번호의 조문이 한 번 더 나옵니다. 조 번호만으로 `MERGE`하면 뒤의 조문이 앞의 조문을 덮어씁니다. 이 파서는 그런 판본의 `pid` 끝에 `@시행일`을 붙여 따로 적재하고 `isCurrent=false`로 표시합니다. 질의에서는 기본적으로 `isCurrent=true`인 조문만 조회합니다.

```cypher
MATCH (a:Article) WHERE NOT a.isCurrent RETURN a.pid AS 조, a.effectiveFrom AS 시행일 ORDER BY 조
```

```text
"폐기물관리법 시행규칙:제10조@20261210", "2026-12-10"
"폐기물관리법:제13조의2@20270708", "2027-07-08"
"폐기물관리법:제68조@20270108", "2027-01-08"
```

    **적재한 조문의 띄어쓰기가 PDF와 다릅니다**

    - 증상: 시행령 제21조 머리글이 「다만, 동일한시ㆍ도에 있는 둘 이상의…」로 붙어 나옵니다(원문 「동일한 시ㆍ도에」).
    - 원인: PDF에서 낱말 사이에 줄바꿈이 있는 위치는 띄울지 붙일지 판단할 정보가 없습니다. 첫 버전에서는 앞줄 끝 여백과 다른 줄에 나온 낱말로만 추정하고, 근거가 없으면 붙였습니다.
    - 조치: 틀린 위치·글·정답과 확인 방법을 적어 다시 요청(위 P5) → `uv run parse_law.py && uv run ingest.py --prune`. 규칙으로 판단하지 못한 위치(약 9%)는 여전히 붙여 둡니다.

    **같은 조 번호가 두 번 나와 서로 덮어씁니다**

    - 증상: 폐기물관리법 제13조의2·제68조, 같은 법 시행규칙 제10조가 PDF에 두 번 나옵니다(끝에 `[시행일: 2027. 7. 8.]` 등). 조 번호만으로 `MERGE`하면 뒤의 조문이 앞의 조문을 덮어쓰거나 항·호가 섞입니다. 부칙의 제1조·제8조도 본칙 번호와 겹칩니다.
    - 원인: 국가법령정보센터 PDF는 시행일이 다른 판본을 같은 문서에 함께 싣습니다.
    - 조치: 부칙은 조문 노드로 적재하지 않고, 시행 예정 판본은 `pid`에 `@YYYYMMDD`를 붙여 따로 적재합니다(`isCurrent=false`). 확인: `MATCH (a:Article) WHERE NOT a.isCurrent RETURN a.pid, a.effectiveFrom`.

    **다시 적재했는데 없어져야 할 관계가 남아 있습니다**

    - 증상: 추출 규칙을 고쳐 `uv run ingest.py`를 다시 실행했는데, 고친 뒤에는 없어야 할 `MENTIONS` 관계 7개가 DB에 그대로 남아 있습니다.
    - 원인: `MERGE`는 추가만 합니다. 이번 추출에서 빠진 기존 노드·관계는 삭제하지 않습니다.
    - 조치: `uv run ingest.py --prune`(`data/`에 9개 법령이 모두 있을 때만). 처음부터 다시 하려면 `uv run ingest.py --reset`.

    **「도지사」로 찾으면 조문이 1건만 나옵니다**

    - 증상: 전문 색인에 넣는 글의 가운뎃점을 「·」로 통일했더니 「도지사」로 찾을 때 조문이 1건만 검색됩니다.
    - 원인: Lucene(전문 색인)이 「·」를 낱말을 잇는 글자로 보아 「시·도지사」·「위치·구조·설비」를 한 낱말로 묶습니다.
    - 조치: 전문 색인용 글(`normText`·`searchText`)은 가운뎃점을 공백으로 바꾸고, 용어 키(`normName`·`normKeys`)만 「·」로 통일합니다(`lawtext.py`의 `search_text` / `norm_key`). 바꾼 뒤 「도지사」 37건, 「위치 구조 설비」 12건이 검색되었습니다.

## 확인 문제

<details class="answer" markdown="1">
<summary>조 수가 PDF와 같으면 적재가 맞았다고 볼 수 있나요?</summary>

아닙니다. 조 수는 맞아도 조 안의 항·호 구조나 글자가 틀릴 수 있습니다. 이 장에서는 조 번호 집합을 비교한 뒤, 구조가 다른 표본 세 개(항만 있는 조, 항 없이 호만 있는 조, 항 아래 호가 있는 조)를 PDF와 맞춰 보았고, 그 과정에서 조 수만으로는 드러나지 않던 띄어쓰기 오류를 찾았습니다.
</details>

<details class="answer" markdown="1">
<summary>P5 프롬프트가 「띄어쓰기 고쳐 줘」보다 나은 점은 무엇인가요?</summary>

틀린 위치(시행령 제21조 머리글), 틀린 글(「동일한시ㆍ도에」), 맞는 글(「동일한 시ㆍ도에」), 고칠 대상(줄바꿈 자리 규칙), 고친 뒤 확인할 것(바뀐 곳의 개수와 예, 세 조문 재대조, 노드·관계 수)을 모두 적었습니다. 그래서 Claude가 수정 결과를 수치로 보고했고, 노드·관계 수가 달라진 이유와 남은 `MENTIONS` 7개까지 드러났습니다.
</details>

<details class="answer" markdown="1">
<summary>MERGE로 적재하면 다시 돌려도 안전한데, --prune은 왜 따로 필요한가요?</summary>

`MERGE`는 이미 있는 것은 두고 없는 것만 더하므로 중복은 생기지 않지만, 규칙을 고쳐 이번 추출에서 사라진 노드·관계를 지우지는 않습니다. 이런 기존 데이터를 삭제하는 옵션이 `--prune`입니다. 지우는 명령이므로 `data/`에 9개 법령이 모두 있을 때만 씁니다.
</details>

<details class="answer" markdown="1">
<summary>시행 예정 조문을 같은 pid로 MERGE하면 어떤 일이 생기나요?</summary>

현행 조문과 시행 예정 조문이 한 노드로 합쳐져 뒤에 읽은 판본이 앞의 판본을 덮어쓰거나 항·호가 섞입니다. 그래서 `pid`에 `@시행일`을 붙여 따로 두고 `isCurrent=false`로 표시해 질의에서 현행 조문만 조회하도록 했습니다.
</details>
