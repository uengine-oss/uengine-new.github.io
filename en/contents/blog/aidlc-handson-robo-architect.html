AI Builds, People Approve — An AI-DLC Hands-On Record and Robo Architect

Date: November 09, 2026

  1. When construction speeds up, inspection gets busier

No matter how fast a building goes up, it is worthless if the blueprint is wrong. When machines can raise a floor in a day, the people who check the drawings and inspect the work set the pace of the whole project.

Software development is seeing the same shift now that AI writes code. The cost of producing code has nearly vanished. But deciding what to build and checking that the result matches the intent is still a human job. AI-DLC (AI-Driven Development Life Cycle), published by AWS Labs, turns this shift into a procedure. AI agents carry out everything from requirements analysis to design, coding and testing. People review and approve the results at every stage.

It sounds convincing on paper. So we ran it ourselves from start to finish and published the whole process and every resulting file as a course.

  2. We actually tried it

We connected AI-DLC 2.11.2 to Claude Code and gave it a one-sentence request: "When a user sends 'find me a 2-hour parking pass near Gangnam Station', build a prototype that recommends the best pass and handles payment and booking. Vue 3 for the front end, Spring Boot for the back end." We ran the same request twice. The first time we took the shortest path to a working app. The second time we produced documents at every stage and had a person approve each one. Here is the record from the second run.

ItemThis run
Stages run17 (team rules → requirements → user stories → screens → domain design → units → API contracts → bolt plan → per-unit build → build & test)
What was built3 services + UI + run scripts (5 units), 6 API contracts between services
Automated tests886 passing, 94–100% line coverage per unit
Approver decisions18 approvals, 3 change requests
AI reviewer passes32 (several sent back as "not ready yet")
Final verdictOf 22 targets: 17 met, 3 not met, 2 unverified. Missed targets were recorded as they were, not lowered
Audit log1,577 entries (questions, answers, approvals and verification results, each with its timestamp)

Getting through the eight design stages, from requirements to the bolt plan, took about 55 minutes. The first service, built test-first, took about 52 minutes. The slow part was not writing code but reviewing and re-testing.

  3. How one line of the request carries through to a test

Every AI-DLC artifact is saved as a file. Below we follow the original request sentence all the way to test code, quoting the real files (translated from Korean; the test code is shown exactly as written).

Original request · [desc]
When a user sends 'find me a 2-hour parking pass near Gangnam Station', recommend the best pass and handle payment and booking
↓ through questions and answers
Requirement · FR1.1 · requirements.md
The system extracts the place (e.g. Gangnam Station) and the duration (e.g. 2 hours) from the Korean voice text the user sends.
↓ into a condition you can check
Acceptance criterion · AC1.1.1 · stories.md
Given the user has started a session, When they send "find me a 2-hour parking pass near Gangnam Station", Then the system reads the place as "Gangnam Station" and the duration as 2 hours and passes them to the recommendation step.
↓ planned test-first

assertThat(parser.parse("강남역 근처 2시간 주차권 찾아줘"))
    .isEqualTo(new ParsedQuery("강남역", 2));
↓ link recorded after implementation
Traceability · traceability.json
{ "id": "AC1.1.1", "status": "OK", "target": "…/search/service/QueryParser.java" }

These are real files from the hands-on artifact repository. Click a name to open the file.

With everything linked by ID, you can trace backwards to answer "why does this code exist?" And when a requirement changes, you can immediately find the tests and code it affects.

  4. What the approver did

AI did most of the work, but there were clear moments when the approver had to decide.

  • Not lowering the bar: The payment service's performance test (respond within 20 ms) occasionally failed because of server load. AI-DLC asked whether to relax the target to 50 ms; the approver kept the target and chose to rerun the test once the load dropped.
  • Accepting a rejection: The AI reviewer found 6 major issues in the screen design and sent it back. The approver had them fixed, then approved.
  • Checking with their own eyes: Even after every test passed, the approver used the app in a browser before approving the final verdict. That is how they found a Korean grammar glitch in the recommendation text (both forms of a particle printed side by side) and logged it as unresolved.

The more work AI takes on, the more it matters to keep approval from becoming a formality. In this run, the approval log records when each approval happened and the answer given, but not who approved. That is a gap to close before using it as a team.

  5. Follow along with the course

We turned this process into an open course at uEngine AX School (in Korean). Every screen comes from a real run, and each chapter has a video.

  • Level 1 (4 chapters): Start from a requirements interview and take the shortest path to a working app.
  • Level 2 (10 chapters): Rebuild the same request with a document at every stage, and see in the real files what each artifact decides and what changed.
  • Theory (4 chapters): Bolts and units, spec gates, version control, and review policies and rollout order, explained alongside the hands-on records.
  • Artifact repository: Every document and line of code from the hands-on runs is public on GitHub. Click a file name in the course to open that file directly.

  6. How it connects to Robo Architect

Work through AI-DLC and you end up asking the same questions: how to define requirements, domain boundaries, screens and units of work, and how to keep the design aligned once the code changes. uEngine's Robo Architect covers the same flow. The difference is how the artifacts are managed. AI-DLC accumulates them as Markdown documents. Robo Architect manages the design as a model and carries changes between the model and the code in both directions.

What the AI-DLC run producedWhere Robo Architect does the same job
Requirements refined through questions and follow-ups, Given/When/Then acceptance criteriaRequirements clarification — split into Epic → Feature → User Story, with questions on ambiguous conditions
↗ See it on the product page
Domain design (components, decision records), units and bolt planDomain and work design — Plan·Task per bounded context, aggregate and EventStorming design
↗ See it on the product page · ↗ EventStorming design
Screen states and interaction specEvent model and screens — commands, events and read models connected all the way to the UI
↗ See it on the product page
Test-first, per-unit build and traceabilityDDD-based automatic code and test generation, commits per task
↗ See it on the product page
Rules learned from change requests (project.md), audit logKeeping spec and code in sync — spec changes flow into the implementation (Spec Align), code changes flow back into the spec (Spec Backfill)
↗ See it on the product page

Today, Robo Architect's design and build skills are based on the spec-kit approach and DDD starter modelling. When you create a proposal you can pick a decomposition mode (Simplified, Detailed DDD, ODA Standard). We are designing a way to let teams choose AI-DLC as a base methodology as well: keep AI-DLC's stage-by-stage approvals and audit log as they are, and bring the results into the design model for code generation and two-way sync between model and code.

If you want to learn the design-to-build flow with AI-DLC first, start with the open course (in Korean). To try the same flow on a design model, follow the Robo Architect tutorial. For training and consulting run on your own team's work, see AX School and Contact Us.
